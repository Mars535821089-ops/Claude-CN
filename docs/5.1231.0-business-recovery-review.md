# Claude 5.1231.0 升级前业务恢复点：已有能力只读评估

## 结论

**以母任务指定的权威工作树当前版本为准，仍没有现成CLI能直接生成并验证完整Claude Desktop业务恢复点。** 本项目的应用/locale备份、5.x元数据材料均不是业务灾备；权威CPS `private_state.py`有可复用的SQLite快照、加密封装和解包校验，以及usage-receipts快照锁，但其当前注册单元直接核查后仍不含Claude，目录采集及通用恢复边界也仍不匹配。此结论不是从主目录旧树推断。

最小方向是：母任务在现有CPS能力上补一个**Claude限定的采集与验证范围**，复用现成底层函数，不另造备份框架，不调用通用生产恢复管线。完成真实采集及隔离恢复演练前，业务恢复点保持**未通过**。

本轮只读代码、静态候选资源和目录元数据；未执行export/inspect/import、SQLite备份、解密、真实备份或恢复，也未提示密码、读取凭据/消息正文。仅新增本文，不改安装入口或CPS实现，不移动现有链接。父级complete-candidate未提交更正保持原样。

### 不能直接复用的高层动作

1. 当前`copy_directory(source,destination)`（285行）明确用`symlinks=False`，会解引用而非保留现有链接；并通配排除`*.lock`、`*.tmp`、`*-shm`、`*-wal`。对活跃SQLite目录可能丢提交，对VM/外置/iCloud目标会改变采集范围，不能直接套用Claude根。
2. 当前`export_state(...)`（496行）先进入`receipt_snapshot_lock()`，再调用`_export_state(...)`（508行）；两者不调用`stop_runtime`，本身不要求退出Codex，但活跃回执服务会让导出拒绝。后者遍历全部CPS units，没有Claude专用选择或跨Claude文件一致性门禁。`include_keychain=False`/`--without-keychain`只跳过专用Keychain payload，**不会排除auth.json、OAuth文件、号池认证文件**。
3. `inspect_or_import(path, apply=False)`（1325行）不是纯文件系统只读：会提示口令，并在默认`tempfile`目录解密出明文。不能以“inspect”名字代替受控私密解包；本轮没有运行。
4. `apply_archive(manifest,keychain,extracted)`（1239行）不是本次生产恢复入口。它调用`stop_runtime(...)`（763行），现有选择含`codex_*`时会请求退出Codex，同时可能停服务/容器；还调用`restore_keychain(keychain)`，并删除/覆盖目录、SQLite WAL/SHM、刷新provider派生配置。不能靠传一个False或省略history消除全部副作用。
5. `install_unit_from(unit,source)`（889行）目录分支先`rmtree`再复制；`restore_keychain(payload)`（939行）会更新旧密钥。两者不能用于本次无条件回灌生产状态。`keychain=None`只保证专用Keychain函数不动作，不解决目录内旧认证文件的重放问题。

CBC封装不是AEAD/独立认证格式，归档内SHA不是签名；复用时至少保留受信的整档SHA、来源、代次及恢复演练回执，不能夸称具备未实现的抗恶意篡改认证。此处不建议另造加密格式。

## 建议母任务选择的最小整合范围

1. **Claude限定单元/采集入口**：纳入两个app support的持久业务存储、经确认的共享`.claude`业务文件、必要的外部工作区/链接目标依赖。排除Codex/CPS账号池及Keychain API；认证文件如确需保密留存，应分组并默认不自动恢复。注册/过滤是当前最小缺口，现有CLI参数不能直接完成。
2. **一致性窗口**：复用SQLite在线备份处理已确认的单库；LevelDB、JSONL、附件/索引关系与VM需证明共同静止点或受支持的快照。必要时仅在获准窗口停止Claude Desktop/Cowork写入者；不要调用CPS全局`stop_runtime`，不要求退出Codex。若共享`.claude`仍有Claude CLI写入，须单独处理，不能假定“Desktop已停”即全部静止。
3. **保留链接和类型**：小幅扩展采集/清单/隔离验证以声明已知链接、目录、权限及必要目标快照；原路径链接保持不动。不要给现有`copy_directory`凭空增加一个尚不存在的CLI flag，也不要通过解引用全部目标“解决”布局。VM base镜像与可写层的范围需分清，不能只收rootfs链接就认定Cowork可恢复。
4. **复用封装和校验**：在已验证PrivateArchive挂载内准备新代次，复用`write_encrypted_archive(..., keychain=None, passphrase=交互内存值)`及`read_encrypted_archive(..., extraction_root=私密新验证目录)`。不调用通用`apply_archive`。源/目标变化、断盘、空间不足或不完整清单须失败关闭；未验证成功前不替换唯一旧恢复集。
5. **真实恢复点验收**：有真实数据归档→逐项/整档hash→新隔离目录解包→SQLite及LevelDB/JSONL与附件关系检查→来源/链接依赖/schema一致性回执；必要的应用级打开验证须另获授权。保留当前最新数据，任何生产恢复都要新代次检查，禁止把旧Keychain、认证状态或旧schema自动覆盖回去。

这五项是小型Claude采集/验证适配，不是重写CPS私密状态框架。当前可直接复用的是上述底层函数；**没有现成的一条安全Claude全业务export/import命令**。本轮未生成或验证真实业务归档，升级前“已验证的数据恢复点”依然是明确缺口，由母任务决定授权、范围和整合。
